The constraint we couldn't see

Hive (us)

  ↓ spawns a child PTY

Crush has the data. We have the image of the data.
(We didn't realize this for ten commits.)
Dead end #1 v1.0 → 1.3

"Let's build our own terminal renderer"

Maybe we parse the ANSI bytes ourselves and render each cell as a React <span>. Full control of every pixel.

src/renderer/src/lib/ansi-parser.ts       ~400 lines
  - VT100 state machine (SGR, CSI, OSC)
  - 24-bit RGB + 256-color palette mapping
  - scrollback ring buffer
  - cursor move / erase / scroll
  - CJK double-width handling (manual wcwidth)
  - IME via hidden textarea
  + 16 unit tests, all passing ✓

Why it failed

  • Perf: 24×80 grid = 1920 React spans per frame. xterm.js uses canvas for a reason.
  • CJK drift: handrolled charWidth() missed edge cases (emoji ZWJ, Hangul Jamo clusters). Every Chinese line accumulated column offset.
  • IME: the textarea-behind-canvas trick has months of xterm.js polish baked in. Ours "couldn't input."
"渲染太慢，没有 xterm 快，还有无法输入。渲染格式对不齐。各种问题。"
Dead end #2 v1.4

"Fine — use xterm's state machine, render our own DOM"

Drop our handrolled parser. Use @xterm/headless — xterm.js's state engine, no renderer. Read the buffer, output React spans.

import { Terminal } from '@xterm/headless'

const core = new TerminalCore(24, 80)
core.feed(ptyBytes)
const cells = core.getRow(0)   //  → Cell[] with fg/bg/bold/etc
// render each cell as a styled <span>
CJK works via @xterm/addon-unicode11

Why it still failed

  • Same perf problem. DOM can't match canvas on 1920 spans/frame.
  • Input path still brittle — our <textarea> captured keys but IME candidate window anchoring was off.
  • We were still looking at pixels, not data.
Dead end #3 v1.5 → 1.5.1

"Don't replace xterm — decorate on top"

xterm.js has registerDecoration(). Keep xterm canvas as the renderer, layer React overlays per buffer line.

const marker = term.registerMarker(0)
const deco = term.registerDecoration({ marker, x: 0, width: 80, height: 1, layer: 'top' })
deco.onRender(el => {
  el.style.background = '#FF60FF'
  el.innerHTML = `<span style="color:#00FFB2">❯</span> ${userText}`
})

What worked

  • Dolly input bar + green ❯
  • RGB-to-Crush color remap for Claude's muted palette
  • Input from xterm worked perfectly

What didn't

  • Decorations overlay — can't truly replace. Still fighting xterm for pixels.
  • Couldn't render tool-call cards, just boxes.
  • Pattern-match on ANSI text → fragile, lossy.
"上面看上去和 term 一样啊。"
The insight

The answer was in claude --help the whole time

--output-format <format>
    Output format (only works with --print):
    "text" (default), "json" (single result),
    or "stream-json" (realtime streaming)

--input-format <format>
    Input format (only works with --print):
    "text" (default), or "stream-json"

--include-partial-messages
    Include partial message chunks as they arrive

--include-hook-events
    Include all hook lifecycle events
Claude Code has the structured JSON pipe we needed all along.
Just not via interactive mode — via --print.
The right path v1.6.0 → now

Structured events → React renderers

# For each chat session: claude --print \ --input-format stream-json \ --output-format stream-json \ --include-partial-messages \ --include-hook-events ↓ stdout: one JSON event per line {"type":"assistant","message":{"content":[ {"type":"tool_use","name":"Read","input":{"file_path":"..."}}, {"type":"text","text":"Here's the file..."} ]}} ↓ main/chat.ts parses + broadcasts via IPC React HiveChat component ├── UserMessage ├── AssistantMessage ← react-markdown, Crush palette ├── ToolBlock ← Dolly left border, per-tool color │ ├── BashHeader Malibu │ ├── ReadHeader Bok │ ├── EditHeader Julep │ ├── TodoInline Charple · ✓→• per status │ └── InlineResult ⎿ + expand/collapse └── status bars rate-limit · model · usage

This is what Crush does in Go. We do it in React. Same idea.

Lessons paid for in calendar days

1. Look for structured APIs before you reach for bytes.
claude --help | grep stream-json would have saved three pivots. Always search the CLI's own docs for machine-readable output modes.
2. Don't fight a canvas renderer with DOM.
xterm.js is 15 years of VT100 edge cases. Trying to match its speed with React spans is a losing race — and every cell-level feature (CJK, emoji, IME) is a new paper cut.
3. Pattern-matching text is a lossy bridge to structured UI.
When the source has types, use the types. Extracting "tool call" from ANSI text works until Claude changes a glyph or a color RGB; then the regex breaks silently.
4. Lock the visual contract before the code.
ui-preview-crush-elements.html became the single source of truth after too many rounds of "is this the right pink?" A static preview with every element mapped to a hex value short-circuits half the review pain.
5. Keep dead paths, but label them.
pretty-term/SUSPENDED.md explains what it was, why it didn't ship, and what's salvageable. Future-you (or a new teammate) doesn't have to read ten commits to learn the same lesson.
6. If the subprocess blocks silently, it's waiting for a reply you didn't send.
v1.7.18: we wired --permission-prompt-tool stdio without implementing control_response. Tracy hung mid-session with zero errors. A whole afternoon lost. The fix was a Zod schema ({updatedInput} / {behavior,message}) we eventually recovered from a captured log. When a handshake is opt-in, the silent-hang mode is always on by default.
